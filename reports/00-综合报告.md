## 0. 结论速览

1. **哨兵导航：不整端采用，按模块摘。** 可直接摘前端 A*/掩码与后端 QP 建模、闭式求解（MIT）；但仓库原样**编译不过**——OSQP/OsqpEigen 子模块未随仓库分发。最省事路径是裁到闭式后端，去掉整个 OSQP 依赖链。
2. **后端耗时长尾有代码级成因**：OSQP 求解器每轮每轴重建、无 warm start，容差 1e-8 / 2 万迭代 / 0.1 s 上限，归一化时间带来 T⁻⁵ 量级权重。作者自测 2026 地图 Minimum Snap 最大 126.7 ms（**本机未复现**）。
3. **雷达只加无线电：可行，且视觉链路可零改动。** 稳定主线不是"三套波形并行"，而是**裁判 0x020E 等级驱动切 profile**：Lv.1/Lv.2 解干扰密钥，Lv.3 才切信息波解 `0x0A01~0x0A05`。最小接入 = 无线电侧 2 个文件改参数 + 宿主侧 4 处接线；三个 glue 模块是纯标准库，可整文件拷入。
4. **必须先过的合规闸**：无线电主体继承南理工 Combat 上游，**上游无 LICENSE**，仓库内部对"是否已解决"两种口径并存。GLM-5.3 组给出最保守判断，见第 4 节。队内技术验证不受此限，但引用/再开源须先落实授权与署名。
5. **更正此前导向的一处错误**：`radar/CombatRadarSdr/phy.py` **不是** IQ 采集入口，只是 GFSK 调制/鉴频数学工具（`gaussian_taps` / `packet_to_iq` / `fm_demod`，全文 40 行）；真正 `adi.Pluto` 在 `apps/jam_rx_app.py:878`、`:1084`，采样率/中心频率/带宽/增益设在 `:447-451`。读代码别从 phy.py 开始。

## 2. TDT 哨兵导航 `tdt-nav-kit`

### 2.1 架构与数据流
纯 C++ 二维栅格组件：前端 `YAstar`（普通 A* + Kinodynamic A*）、后端 `MinimumSnapOsqp`（分段多项式 + 方形走廊 SFC），`main.cpp` 只是基准/可视化测试台（1000 组随机点对，`main.cpp:455-497`）。**全仓没有 ROS 节点、串口/套接字、控制循环、重规划触发或指令下发**——这不是能跑的导航系统，只是规划内核。

### 2.2 硬伤：原样编译不过（多组一致）
- `3rd/` 只有 `.gitkeep`（`.gitignore:7-9`）；`.gitmodules` 声明了 `osqp` / `osqp-eigen` 但**没有 gitlink、无固定版本**，子模块根本没随仓库提交。
- `scripts/setup.sh:29` 的 `git submodule update --init` 拉不到对象，`:31-34` 随即检查两个 CMakeLists 并报错退出。
- 但 `CMakeLists.txt:13-14` 强制 `find_package(osqp)` / `find_package(OsqpEigen)`，`:30` 链接 `OsqpEigen::OsqpEigen`；`minimumSnap.hpp:17` 无条件 `#include <OsqpEigen/OsqpEigen.h>`；`minimumSnap.cpp:870` 实例化求解器。
- **低风险裁剪**：闭式求解器只用 Eigen 分解（`minimumSnap.cpp:594-700`），删掉头文件包含与 `osqpExecute`（`:782-905`）即可彻底去掉 OSQP 依赖（hy4free-#1、m2b 一致）。

### 2.3 关键实现与风险（模型一致项）
- **前端**：八邻域 A* + 人工势场；带时限的多层位掩码 `Mask`（`yastar.cpp:451-506`）按持续时间过期、按数量淘汰最旧层——**这是雷达/无线电解出的动态障碍注入的现成钩子**，也是与无线电最自然的对接点（hy4free-#1、m1）。
- **后端分派不一致**（已回源码复核）：`minimumSnap.hpp:172` 默认 `Backend::Close`，但 `minimumSnap.cpp:172-175` 的 `autoBackend()` 直接 `return Backend::OSQPCorridor`，注释"现在的 backend 不挑条件…等 sfc 整好了再换"。头文件里写了三种后端与推荐顺序（`OSQPCorridor > Close > OSQPPath`，`hpp:33-40`），**实际没有按地图/成功率/时序触发的自动切换**，也没有 OSQP→闭式的回退：求解失败直接返回空（`:273-278`、`:888-893`）。`main.cpp:163` 注释说"回退闭式"，代码里不存在（hy4free-#1、m2b、m6 一致）。
- **解的唯一性与 success 语义**（最终版 m2b）：约束 5n-1 条对 6n 个未知数，零空间至少 n+1 维；`closeSolver` 用 `completeOrthogonalDecomposition`（`minimumSnap.cpp:692`）而非 Cholesky，等于承认约化 Hessian 可能不满秩，OSQP 与闭式可能选出不同解（`main.cpp:309` 的双后端对比正是此风险的动机）。`success` 由 `bad.empty()` 决定（`:159-163`），迭代耗尽仍返回最后一条轨迹，故 `success=true` 只代表最后一次采样没检出碰撞。
- **长尾成因**（m2b 最详细）：每轮每轴重建 solver 无 warm start（`:870-887`）；`tol=1e-8` + polish + `maxIter=20000`（`:872-875`）在归一化时间 T⁻⁵ 量级 Q 上磨精度（`:333`），撞 0.1 s 单轴上限（`:876`）；A/Q 每轮 dense 构造再 `sparseView`（`:860-861`）；`timeLimit` 只在整轮末检查（`:161`）。
- **前端代码级缺陷**（m1、m6 一致）：`yastar.cpp:818/822` 用 `>` 而非 `>=`，`x==cols` 可越界写 `nodeMap`（`:827`）；`search` 失败返回 `{start}` 而非空（`:879`），导致 `main.cpp:128` 的 `path.empty()` 永不成立，失败静默流入后端被当作单点路径；A* 堆无 decrease-key / 无陈旧项判断（仅 `closed` 剪枝）；`getSDF` 的 cv 分支 `dst=dst*mapping`（`:560`）是重新绑定而非原地缩放。
- **坐标约定坑**（m2b）：`lineInObsticle` 用 `(p-origin)/mapping`（`minimumSnap.cpp:711-714`），`SfcSquare` 内部用 `(x+origin)/mapping`、输出 `left*mapping-origin`（`sfcSquare.cpp:145-146,228-231`），前端恰好相反（`yastar.cpp:884,889`）；示例里地图原点恒为 0 掩盖了错位，接入真实定位原点后走廊会与碰撞地图错位。
- **无碰撞硬保证**：SFC 文档自承"不能保证轨迹不撞墙、也不能保证走廊相接"（`doc/MinimumSnap.md:196`）；非严格碰撞检测容忍 2 个障碍栅格（`minimumSnap.cpp:737-749`）；`SolveInput` 注释明确"迭代次数耗尽时返回的轨迹仍可能有碰撞"（`minimumSnap.hpp:47`）。上层必须自加安全兜底。
- **C++ 标准被低估**：README 称 C++11，实际用到 `span`（`yastar.cpp:681`）、`clamp`/`ranges`，而 `CMakeLists.txt:4-5` 把 CXX_STANDARD 注释掉了。

### 2.4 选型：以我为主、按模块摘
**可直接摘**：QP 矩阵构造与闭式求解（`minimumSnap.cpp:317-583`）、`lineInObsticle` DDA（`:709-730`）、`YAstar` + `Mask` 带时限接口、Felzenszwalb 精确 EDT 回退（`yastar.cpp:565-745`）。MIT，无通信代码。
**必须改/补**：控制循环与重规划触发、地图/定位替换（写死图片 + Y 翻转，`main.cpp:76,79-91`）、通信层（把无线电障碍喂入 `yastar.cpp:451`）、>= 边界与失败返回空、堆陈旧项、origin 符号统一、真回退 + 错误码、CMake 补 CXX_STANDARD 与库目标、ROS2 桥（无 `package.xml`/`rclcpp`/消息定义，`setMap` 两个重载障碍语义相反 `yastar.hpp:102,111`）。
**换分支触发条件（代码里的硬体现）**：Kinodynamic A* 节点预算打满静默失败（`kinodynamicAstar.cpp:209-211`）、OSQP 不收敛返回空解（`minimumSnap.cpp:888-893`）、单次 solve 推过 100 ms（`:876` 作者自划线）、二维栅格表达不了坡道/隧道。前两条说明**库内没有降级规划器**，若搜索失败率不可接受，要么自加 fallback、要么换算法分支；不要在本库内继续打补丁（`doc/MinimumSnap.md:405` 作者亦承认这套线性 QP"基本已经到头"）。 但反过来说（最终版 m2b 补充）：若只需在稀疏障碍场地给出平滑可跟踪的 2D 轨迹，改完必改项后性价比仍然很高——纯 QP、无非线性迭代、单次求解毫秒级；结构上限只在要求硬保证无碰撞或加速度上限时才成立。

## 3. TCR 无线电（只加无线电的最小接入）

### 3.1 端到端链路（更正后）
`AD9361（adi.Pluto，jam_rx_app.py:878/1084，参数 :447-451）→ GFSK 解调/软判决（phy.py 只提供数学工具；parser/info_wave_fast_decoder.py 才是解码主力）→ server_comm.py TCP server 127.0.0.1:5000 → ground_vision/radio_bridge.py（client）→ position_fusion.py 与视觉快照仲裁 → 裁判串口`。

### 3.2 稳定主线真相（hy4free-#2、m4b 一致）
不是三次波形并行，而是**同一块 AD9361、同一通道按干扰等级切频点**：裁判 `0x020E` 等级 → `JamLevelState`（`jam_level_state.py:37-52`，只接受 1..3）→ 地面以 `0xFF+level+0xFE` 下发（`radio_bridge.py:383-394`、`server_comm.py:296-300`）→ 接收侧 `INFO_MODE_LEVEL=3`（`jam_rx_app.py:80`）、`should_use_info_mode` 默认 `level>=3`（`:330-335`）→ `get_receiver_profile` 在 6 个 `JAM_PROFILES` 与 2 个 `INFO_PROFILES` 间二选一（`:338-348`，频点见 `radio_profiles.py:21-34`）。Lv.1/Lv.2 解 `0x0A06` 密钥，Lv.3 才解 `0x0A01~0x0A05`。比赛入口固定 `--parse-policy default`（`match_rx_gui.py:427-434`），`start.sh` 菜单 1 指向 `match_rx_gui.py`。

### 3.3 协议与解码（m3b 组，唯一带本地实测）
- 帧：`A5 + len(LE) + seq + CRC8 + cmd_id(LE u16) + data + CRC16(LE)`（`protocol.py:51-62`）；空口包 = 8B 访问码 + 2×u16(15) + 15B payload = 27B/216bit（`:65-70`）。访问码 `0x2F6F4C74B914492E` / `0x16E8D377151C712D`（`:3-4`），两码汉明距实测 26 bit。
- **CRC 实测**：`crc8_maxim("123456789")=0x0B`（非 MAXIM-DOW 的 0xA1）、`crc16_ibm=0x6F91`（即 MCRF4XX）——两端同源自洽，**按函数名猜标准算法去对接外部实现必错**。
- 软判决（`info_wave_fast_decoder.py:559-612`）：96 bit 已知段最小二乘估 scale/门限 → 全帧硬判 → 保留软值；`sps=47`、`bt=0.35`、`fs=1M` → 21276.6 bps，216 bit 空包 10.15 ms；`sensitivity` 是 rad/sample（`phy.py:32`），1.5628 对应 248.7 kHz 频偏，正好填满 info 的 540 kHz 带宽。**这些数值只在 fs=1 MHz 下成立**。
- 抗假 SOF 的关键：CRC16 失败只丢 1 字节重同步（`info_wave_fast_decoder.py:429-438`）；`_parse_buffer` 用 `INFO_COMMAND_LENGTHS` 强校验长度（`radio_bridge.py:408-445`）。
- **另两处工程债**（最终版 m3b 新增）：legacy 路径 `valid` 不含 CRC（`gnuradio_frame_parser.py:387`），`extract_frames` 只拦 `data_len>256`（`:507`）且不校验 cmd_id 白名单，假 SOF 凑出合法 CRC8（1/256）即可注入最长 256B 伪帧并吞掉后续真帧；`0A01` 端序自动纠正只在越界时单向切 big、不切回（`jam_rx_app.py:737-752`），一次误判会让后续所有帧按大端解释。测试全部用合成 IQ，无真实录包回归（`experiments/results/*.json` 引用的 c64 未随包分发）。
- 本地复现：`test_info_wave_fast_decoder.py` 9 项全通过（1.888 s），覆盖 47 相、buffer 边界、非固定包间隔、0A05=41B、1/2 bit 修复。
- **最脆的判别**（按最终版 m3b 的精确推导）：`max_access_errors=24`（37.5%）实际被 `info_jam_access_margin=2` 压到约 12 bit——真 INFO 访问码错 k 位时 jam 距最坏 26-k，判据 26-2k≥2 → k≤12；反向 JAM 码需错 ≥14 位才可能被误判成 INFO，两侧边界只隔 1 bit，24 这个旋钮基本惰性。建议把 `max_access_errors` 降到 12 左右或与 margin 解耦，并用真实录包统计误分类率。

## 6. 最终建议

**哨兵线**（对应此前"直接采用还是换分支"）：
- 主线采用 TDT 规划内核并改进，**不换算法分支**；把"换分支"降为仿真对照（Fast-Planner / EGO-Planner），有瓶颈证据再升级。
- 第一步先做**裁剪编译**：删 OSQP 依赖 → 用闭式后端作常备兜底（结果确定、无迭代、适合算力受限平台）；走廊式 OSQP 作为可选增强，且必须补超时降级（退回前端路径直跟）。
- 必改清单：`>=` 边界、失败返回空、堆陈旧项、origin 符号、真回退、CMake/语言标准、ROS2 桥与安全兜底。
- 与无线电的联动点：`yastar.cpp:451-506` 的带时限掩码接口，可把雷达/无线电全场坐标作为动态障碍喂入——两块改动能打通。

**雷达线**（只加无线电，视觉链路不动）：按 3.4 的 5 步清单接；`radio_bridge.py`/`position_fusion.py`/`jam_level_state.py` 整文件拷入；视觉/相机/模型/`counter_drone` 零改动；排除所有实验分支；联调先无硬件后发射。

**两条线共用的前置**：2027 规则与串口协议核对、裁判系统反向工程限制、许可证链落实（尤其 Combat 上游）。
