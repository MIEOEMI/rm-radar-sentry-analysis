# TDT 哨兵导航前后端源码精读与选型报告

本报告逐文件核对东北大学 T-DT 战队 2026 赛季开源的哨兵导航组件，仓库仅 main 分支，采用 MIT 许可，版权人为 Rongxuan Ye 与 BoLin Li（LICENCE:1-3），与 README 署名不一致（README:163）。README 把 YAstar 定义为前端、MinimumSnapOsqp 定义为后端（README:3、README:13-14），核心为四个 C++ 类，约三千七百行。以下每条结论都标注文件与行号，读不到的实现或存疑处直接说明，不补写文档里没有的细节。

一、第三方依赖核实。仓库 3rd 目录实际只有一个零字节占位文件（3rd/.gitkeep），gitignore 明确忽略 3rd 下全部内容（.gitignore:7-9）。gitmodules 声明了 osqp 与 osqp-eigen 两个子模块地址（.gitmodules），却没有固定版本；git 索引里没有任何 160000 模式的 gitlink，submodule 状态为空，git/modules 目录也不存在，说明两个子模块根本没有随仓库提交。因此 setup 脚本的 submodule 初始化命令拉不到对象（scripts/setup.sh:29），随后检查两个 CMakeLists 时必然报错退出（scripts/setup.sh:31-34）。README 声称固定版本子模块已放在 3rd（README:41）与实况不符，版本号只出现在手动安装命令里，分别是 v1.0.0 与 v0.11.0（README:52、README:61）。由此产生硬依赖链：构建脚本强制查找 osqp 与 OsqpEigen（CMakeLists.txt:13-14）并链接 OsqpEigen（CMakeLists.txt:30），后端头文件无条件包含 OsqpEigen 头文件（minimumSnap.hpp:17），求解器实例化 OsqpEigen（minimumSnap.cpp:870）。结论是这份压缩包原样编译不过 MinimumSnap 的任何翻译单元，选型前必须先系统安装这两个库或修复子模块。值得注意的是闭式求解器只用 Eigen 的矩阵分解（minimumSnap.cpp:594-700），运行期完全不依赖 OSQP；若只保留闭式后端，删掉头文件里的包含和 OSQP 求解函数（minimumSnap.cpp:782-905）即可彻底去掉该依赖，这是低风险裁剪路径。

二、逐文件实现要点。main.cpp 是基准与可视化程序，不是可执行节点：主函数跑一千组随机点对（main.cpp:455-497），三处读固定地图图片（main.cpp:76、main.cpp:228、main.cpp:393），用 OpenCV 显示（main.cpp:198），并手工做世界坐标与图像坐标的 Y 轴翻转（main.cpp:79-91），参数集中在 main.cpp:144-164，地图原点恒为零（main.cpp:94、main.cpp:148）。前端 yastar 是八邻域 A 星加人工势场，类注释自称基于 A 星修改的雷达重投影类（yastar.hpp:52），掩码被注明用于雷达障碍点映射（yastar.hpp:300）；掩码用位压缩管理多层（yastar.hpp:21-34），带时限的掩码接口按持续时间过期、按数量淘汰最旧层（yastar.cpp:451-506），这正是雷达动态障碍注入的现成钩子，也是与无线电数据对接最自然的入口。代价地图初始化有稀疏分支：有 OpenCV 时调用距离变换（yastar.cpp:553-562），否则走纯 C++ 的 Felzenszwalb 线性距离变换（yastar.cpp:565-745），后者用到 C++20 的 span（yastar.cpp:681）。搜索每次自动重置并重建代价地图（yastar.cpp:803-811）。动力学 A 星继承前端（kinodynamicAstar.hpp:11），状态含速度（kinodynamicAstar.hpp:15），终点邻域用三次多项式直连（kinodynamicAstar.cpp:172-191）；文档自述其全局搜索约两秒并建议前后端分离（doc/Astar.md:90），故不宜作哨兵主规划。后端 minimumSnap 完成二次规划建模（minimumSnap.cpp:317-505），提供三种后端，推荐优先级为走廊式 OSQP 大于闭式大于纯 OSQP（minimumSnap.hpp:33-40），默认却是闭式（minimumSnap.hpp:172），归一化时间默认关闭（minimumSnap.hpp:173）。碰撞检测在非严格模式下容忍两个障碍栅格（minimumSnap.cpp:737-749）。方形走廊头文件自嘲其实不算走廊（sfcSquare.hpp:3），文档明确它不能保证轨迹不撞墙、也不能保证走廊相接（doc/MinimumSnap.md:196）；去冗余逻辑被注释未启用（sfcSquare.cpp:117-119），膨胀函数的并行参数两路代码相同且 omp 被注释（sfcSquare.cpp:499-509）。

三、可直接摘与必须改。可直接摘的是纯算法部分：全仓没有 ROS 节点、串口/套接字通信或发布订阅等通信实现，QP 矩阵构造、闭式求解、曲线解码、梯形时间分配（minimumSnap.cpp:281-583）、动力学 A 星、方形走廊、前端与掩码都可整体搬用，且为 MIT。必须改的有八处：主程序没有控制循环、重规划触发和指令下发，需自写节点（main.cpp:455-497）；地图写死为图片且 Y 翻转写死，需换真实栅格与定位（main.cpp:76、main.cpp:79-91）；通信层完全缺失，无线电解出的障碍点须自行喂入带时限掩码接口（yastar.cpp:451），同级 RM_sdr 是 GNU Radio 的 Python 工程，不在此 C++ 仓库内；README 称只需 C++11（README:41），但代码用了 span、clamp 与 ranges（yastar.cpp:681、sfcSquare.cpp:564、yastar.hpp:328），实为 C++17/20，而构建脚本把标准设置注释掉了（CMakeLists.txt:4-5）；两个前端头文件用 __has_include 条件包含 OpenCV（yastar.hpp:15-17、sfcSquare.hpp:12-16），故 README 所说 OpenCV 仅用于示例并不准确（README:47）；构建只产生单一可执行文件 play，没有库目标与安装规则（CMakeLists.txt:19-31）；迭代次数耗尽仍可能返回带碰撞的轨迹（minimumSnap.hpp:47），上层必须加安全兜底；性能数据在桌面 CPU 上测得（README:114），2026 地图后端最大耗时约一百二十七毫秒（README:132），嵌入式平台需重调迭代数与求解时限。示例里的速度测试只用两条固定速度约束、遍历两个后端做正确性对比（main.cpp:227-388），并非覆盖性验证，接入后仍须自建回归用例；这也说明两后端的差异目前只由示例参数体现，没有工程级的自适应判据。

四、换分支触发条件在代码里的体现。仓库只有 main 分支，因此这里的换分支指运行期与编译期的算法分支而非版本控制。顶层分派集中在 solve 函数（minimumSnap.cpp:257-278）：无效输入转自动选择（minimumSnap.cpp:258-261），闭式走等式求解（minimumSnap.cpp:262-272），两种 OSQP 走带走廊的迭代求解（minimumSnap.cpp:273-276）。自动选择函数实际只有一行直接返回走廊式 OSQP 并注明现在不挑条件、等走廊做好再换（minimumSnap.cpp:172-175），也就是说代码里不存在按地图、成功率或时序触发的自动切换，所谓条件仍是待办。示例注释写了回退闭式（main.cpp:163），但分派函数与求解器失败时都直接返回空结果（minimumSnap.cpp:278、minimumSnap.cpp:888-894），并没有 OSQP 到闭式的回退，示例里遍历两个后端只是对比测试（main.cpp:309）。求解器硬阈值为零点一秒时限、两万次迭代、一亿分之一容差（minimumSnap.cpp:873-876）。碰撞迭代的终止条件是求解成功、迭代耗尽或超时（minimumSnap.cpp:161），每轮按轮次奇偶二选一：偶数轮插入中点并生成新走廊，奇数轮把碰撞段两侧走廊各缩一半（minimumSnap.cpp:957-989），闭式后端则是偶数轮插点、奇数轮把分段时长乘零点八（minimumSnap.cpp:1016-1026）。编译期分支还有归一化时间（minimumSnap.cpp:324、minimumSnap.cpp:374、minimumSnap.cpp:569，main.cpp:162 称其实验性）、严格碰撞（minimumSnap.cpp:744）、稀疏 SDF（yastar.cpp:762、yastar.cpp:777）以及 OpenCV 条件编译（minimumSnap.hpp:207-210）。另有一处隐蔽移植坑：方形走廊的坐标变换用加原点入、减原点出（sfcSquare.cpp:145、sfcSquare.cpp:228），前端恰好相反（yastar.cpp:884、yastar.cpp:889），后端碰撞检测也用减（minimumSnap.cpp:712），仅因示例原点为零而未暴露，接入真实定位原点后走廊会与碰撞地图错位。

五、选型结论。雷达已获国一、只补无线电的前提下，值得摘的是前端与掩码时限接口（雷达障碍注入钩子，不含通信代码，可自行接无线电）以及后端 QP 建模与闭式求解；不建议整包接入。理由是 OSQP 子模块缺失必须补依赖或裁到闭式，主程序、构建、语言标准与 OpenCV 隐含依赖都要改，且无回退、无碰撞硬保证、无重规划循环，安全兜底与无线电链路全需自研，动力学 A 星又太慢（doc/Astar.md:90）。当前代码里唯一能挂接降级或重规划的信号是求解失败标志（minimumSnap.hpp:179-185）、OSQP 未收敛（minimumSnap.cpp:888-894）与迭代耗尽（minimumSnap.cpp:161），其余自动换分支均为待办。后端取舍上，闭式求解无迭代、结果确定，适合在算力受限的哨兵上作常备兜底；走廊式 OSQP 质量更高（minimumSnap.hpp:34），却依赖求解器零点一秒内收敛（minimumSnap.cpp:876），宜作为可选增强而非默认，这样也顺带绕开缺失的子模块依赖。
